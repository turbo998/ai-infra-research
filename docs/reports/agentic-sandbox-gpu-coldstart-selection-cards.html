Perturbation & Consistency Analysis

1. 为什么 Tier 3 在 1,000 RPS 下仍能保持 295.0 ms？ 因为同一个基础环境的百个沙箱共享宿主机 OS Page Cache 中的同一份只读 Golden Memory File，UFFD 缺页拷贝完全在宿主机 DRAM 内部完成（~50 GB/s），零磁盘读取放大。

2. 1,000 RPS 下 Tier 4 的带宽护栏：当同一节点瞬间唤醒多个 14GB 模型时，单机 PCIe/RDMA 带宽会出现排队（P99 从 485ms 升至 620ms）；生产调度器需开启 Locality-Aware 权重亲和调度，优先将请求路由至已缓存该模型权重页的节点。

Robustness Conclusion: Page-cache-backed COW memory snapshots (Tier 3) and P2P RDMA weight pools (Tier 4) convert an O(N) registry/disk I/O storm into an O(1) memory-mapped operation.

7 / 7 · MY TAKE Architect Playbook & Readiness

架构师决断：何时选 Firecracker MicroVM，何时选 CRIU + cuda-checkpoint，何时选 Lazy OCI？

给企业 CTO 与 AI 基础设施团队的最终生产落地方案与禁区清单。

✅ Good fit (强烈推荐)

  • 多租户 Coding Agent / 自动化测试 / 浏览器工具沙箱 → 选 Tier 3 (Firecracker + UFFD)：KVM 硬件虚拟化独立内核防逃逸，125.0 ms 瞬间唤醒，单机混部 80 沙箱，成本立省 73.8%。
  • 百个微调垂类大模型 / 多租户 Serverless GPU 推理 → 选 Tier 4 (CRIU + cuda-checkpoint + RDMA 流)：420.0 ms 恢复 GPU 上下文与 14GB 权重，热池砍至 4.0%，月度算力立省 77.3%。
  • 存量标准 K8s 无侵入提速 → 选 Tier 2 (SOCI/eStargz + Safetensors mmap)：无需改业务代码即可将冷启动从 25.5s 压至 5.2s。

⛔ Not for (严禁踩坑)

  • 严禁在共享宿主机内核的普通 Docker 容器中裸跑大模型生成的代码：一次内核提权漏洞即可击穿整台 GPU 节点。
  • 严禁将 10GB+ 模型权重直接打入 Docker 镜像层或使用旧版 Pickle torch.load：引发双倍内存占用与 20 秒级拉取解压风暴。
  • 严禁在未重置随机数熵池 (vmgenid) 的情况下一对多克隆 VM/CRIU 快照：会导致并发沙箱生成相同的 TLS 密钥与 UUID。
