为什么 `ncclCommShrink` 比传统重启快两个数量级？

  • 免除容器与 CUDA Context 重建 (`480s -> 12s`): 传统重启必须卸载驱动上下文、重拉容器镜像并重新编译 TorchInductor 图；原地重构保留存活 127 台节点的所有进程内存与显存页表。
  • 免除慢速全量读盘 (`240s -> 8s`): 仅替补节点或通过本机锁页内存/兄弟节点 RDMA 恢复最新状态。
Verifier Reproducibility: 运行 python -m unittest tests/test_gpu_cluster_fault_recovery_selection.py 可在本地秒级完成校验。

为什么 256 卡看不出隐患，到 1,024 卡就爆发？

在 256 卡集群上，每天仅发生约 1 次故障，即使每次停机 57 分钟，全天有效算力率仍有 96.04%，极易让团队产生“重启脚本够用”的错觉；一旦扩容到 1,024~2,048 卡，每天 4~8 次故障直接吞噬 16%~32% 的总算力。

5 分钟异步 DCP 如何助攻 Tier 3？

结合 Round 3 的两阶段异步 DCP（每次存盘仅冻结 GPU `3.125s`），将存盘间隔从 30 分钟缩短到 5 分钟不会损伤正常训练吞吐，却直接把每次故障的平均回滚白跑时间从 `900.0s` 砍到 `150.0s`。

Robustness Takeaway: 架构师在设计 ≥ 512 卡集群方案时，必须将“单次故障恢复总耗时 ≤ 4 分钟”作为硬性验收指标写入技术标书。

7 / 7 · MY TAKE · GOOD FIT VS NOT FOR & READINESS ARCHITECT PLAYBOOK

架构师选型决断：512~1,024 卡必上 `ncclCommShrink` + 5m 异步 DCP，超千卡副本组上 `TorchFT`

千卡集群的稳定性不是靠“祈祷硬件不坏”实现的，而是靠“坏一台节点时其余 127 台节点进程不死、28~215 秒内热替换自愈”的软件工程体系保障的。

✅ Good Fit (强烈推荐适用场景)

  • Tier 4 (`TorchFT` / Replica-Group Peer RDMA): ≥ 1,024 GPUs、采用 Hybrid-FSDP (HSDP) 或 DiLoCo 多副本组架构的长周期预训练集群（零回滚，Goodput 99.87%）。
  • Tier 3 (`ncclCommShrink` + 5m Async DCP): 512 ~ 1,024 GPUs 全局緊耦合 3D 并行 (TP+PP+CP+FSDP) 生产集群（Goodput 99.00%，月省 $277k）。
  • Tier 2 (Flight Recorder + 暖备节点替换): ≤ 256 GPUs、不允许改动训练框架源码的快速上线场景（Goodput 98.58%）。

⛔ Not For (严禁误用边界)

  • 严禁在生产千卡集群保留默认 30 分钟 `NCCL_TIMEOUT`: 任何单点静默假死都会让上千张 GPU 陪绑空烧半小时。
  • 严禁在未开启 Flight Recorder 时排查集合通信挂起: 缺少 Op ID 环回日志会导致全网堆栈一致、无法自动定位坏节点。
  • 严禁在单副本无冗余拓扑强套 Tier 4 内存直传: 若全集群仅有一份模型分片且无兄弟副本组，仍需使用 Tier 3 配合 5m 异步 DCP 恢复。
