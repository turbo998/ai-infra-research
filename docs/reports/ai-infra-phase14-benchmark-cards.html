7 / 7 MY TAKE · ARCHITECTURAL DECISION GUIDE & READINESS

架构师选型决断：何时启用 GDAKI / DP-Attention / SRAM 级联，何时规避反模式？

✅ Good Fit（强烈推荐场景）

  • 跨机柜 Wide-EP MoE Decode（EP ≥ 32）：启用 DeepEP V2.5 NCCL_GIN_TYPE_GDAKI，配置 kNumQPs = 1 + kNumSMs（如 25 QPs）与 ncclGinOptFlagsAggregateRequests，消除 CPU Proxy 瓶颈。
  • MLA 架构长上下文高并发推理（DeepSeek-V3/R1）：采用 SGLang dp_attention（DP_attn=64, EP=64），开启 SUM_LEN + FP8 AllGatherv + TBO，释放 9.34x KV 容量。
  • 64K+ Agentic 代码生成与多轮工具调用：单集群开启 vLLM V1 SuffixDecodingProposer + DFlashProposer；跨集群采用 片上 SRAM 8K 滑窗草稿 + GPU HBM3e 64K 全量验证。

⛔ Not For（严禁误用场景）

  • 在 GDAKI 下配置过少或过多 QP：kNumAvailableQPs < kNumSMs 会退化为全卡 L2 自旋锁（+49.97 us）；超过 64 QPs/rank 则引发 NIC ICM 页表抖动。
  • 在 pplx 对称后端或 CUDA Graph 下强开 SUM_LEN：空闲 0-Token DP Rank 会导致设备端握手死锁，必须走 MAX_LEN 并开启 mask_dp_pad_moe_topk_ids（-1 哨兵）。
  • 用纯片上 SRAM 集群直接硬扛高并发 64K–128K 全量 KV：单会话 10–20 GiB KV 会瞬间击穿片上 SRAM 并触发片外 MemoryX 带宽雪崩（TPOT 劣化至 348+ ms）。
