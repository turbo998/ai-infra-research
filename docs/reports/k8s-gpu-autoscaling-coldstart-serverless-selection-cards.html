✅ 为什么 safetensors mmap 在本地 NVMe 上还要 19.5 秒？
70B 模型有 80 层、上千个独立权重 Tensor。默认加载器逐个解析元数据并触发内核缺页中断（4KB Page Fault），根本喂不饱 PCIe Gen5 带宽；块对齐直接 64MB 连续 DMA 仅需 1.5~3.4s！
✕ 为什么不设 `VLLM_CACHE_ROOT` 每次重启都要白等 98 秒？
vLLM / SGLang 启动时会用 Triton 编译融合算子并录制多档位 CUDA Graph；若不把缓存目录挂载到宿主机持久化盘，每次扩容新 Pod 都会从头重编 98 秒！
Matrix Summary: Tier 2 cuts cold start by 6.8× using standard K8s volumes; Tier 3 & Tier 4 break the 5-second barrier to unlock true Scale-to-Zero economics.

  maxReplicaCount: 16

    - type: prometheus

void fast_restore_partition(void* d_hbm_base, size_t total_bytes, int peer_node_rank) {
  #pragma omp parallel for num_threads(8)
  for (size_t offset = 0; offset < total_bytes; offset += (64ULL << 20)) {
    rdma_gpudirect_read_async(d_hbm_base + offset, peer_node_rank, offset, 64ULL << 20);
  }
  cudaStreamSynchronize(restore_stream);
  rebind_precaptured_cuda_graphs(d_hbm_base); // 0.2s 指针重绑定，立即可服务！
}

🔍 为什么网关 Activator 请求缓冲池必不可少？
当某个缩容至 0 的长尾模型突然收到请求时，Knative Activator / AI 网关会先将 HTTP 连接 Hold 在网关内存里 `1.8~4.6 秒` 等待 GPU 唤醒，对客户端完全透明（只体现为首字稍慢，绝不报 502/503 错误）！
⚡ 为什么缩容窗口必须设为 300~600 秒？
大模型单次加载涉及 70GB 数据搬运；若缩容太激进（如 30 秒无请求就缩容），用户阅读上一轮回答的 45 秒停顿就会触发缩容，下一句追问又得重新冷启动！
Robustness Conclusion: Scaling on unbounded queue depth (`num_requests_waiting`) enables proportional multi-replica jumps (`1 → 5 → 16 Pods`) in a single KEDA control cycle.

7 / 7 · MY TAKE · GOOD FIT VS NOT FOR & PRODUCTION READINESS Architect Decision Guide

架构师总结：KEDA 队列指标管扩缩，cuda-checkpoint 与块对齐 P2P 管秒级唤醒

彻底终结“要么白烧整晚闲置 GPU、要么早高峰卡死 5 分钟”的两难困境。

✅ Good Fit (强烈推荐场景)

  • • 多租户/多垂类模型混部 Serverless 平台 → Tier 4 (ServerlessLLM 块对齐 + RDMA P2P)：1.8s 唤醒，支持真正 0 显存闲置，月省 68.4% 算力费。
  • • 单机多模型分时复用 / 快速容灾切换 → Tier 3 (CRIU + cuda-checkpoint)：4.6s 从主机内存原位恢复完整 CUDA Graph 上下文。
  • • 主力大模型动态扩缩容 → Tier 2 (KEDA 排队/KV 触发器 + NVMe 编译缓存)：当天即可落地的云原生改造。

⛔ Not For (严禁踩坑场景)

  • • 严禁用 `DCGM_FI_DEV_GPU_UTIL` 作为 LLM HPA 指标 (Tier 1)：Batch=1 即显示 94%，10× 洪峰封顶 100%，必然导致错配与雪崩。
  • • 严禁在不挂载 `VLLM_CACHE_ROOT` 的情况下频繁扩缩 Pod：每次扩容白花 98 秒重编 Triton 与 CUDA Graph。
  • • 严禁在 Scale-to-Zero 场景缺少网关请求暂存层 (Activator)：唤醒期间的新请求若无网关 Hold 队列会直接报 503 错误。
🛠️ 生产上线 4 步核验清单 (Production Readiness Checklist)

1. [ ] 部署 KEDA 并绑定 vllm:num_requests_waiting 与 vllm:gpu_cache_usage_perc，下线基于 GPU_UTIL 的 HPA。
2. [ ] 将 VLLM_CACHE_ROOT 与 TORCHINDUCTOR_CACHE_DIR 挂载至节点持久化 NVMe，消除 98 秒图编译开销。
3. [ ] 引入块对齐 DMA 加载（ServerlessLLM / fastsafetensors GDS）或 cuda-checkpoint 主机内存休眠。
4. [ ] 设置扩容零延迟 + 缩容 300~600s 防抖冷却窗口，并在网关层启用请求暂存队列（Activator Hold）。
