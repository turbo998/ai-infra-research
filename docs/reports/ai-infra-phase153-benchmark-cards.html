2 / 7 · SCENARIO: KDA KCP RECOMPUTE, MI355X MONO DECODE & NIXL CPU PROXYDEEP DIVE

单案深挖：KCP 无通信重计算省 41.7% Workspace，NIXL 多线程 CPU Proxy 吞吐提升至 510 Kops/s

聚焦 Blackwell TMEM 释放栅栏、ROCm MI355X TP8 单体解码与 GPU 发起的 NIXL CPU Proxy 工作线程池。

Scenario A · FlashInfer KDA TMEM Epilogue Release & Comm-Free KCP Recompute (#7828 / #7846 / #7841)

问题：Compute Warp 写入 TMEM 映射表后未向 Prefix Epilogue 释放栅栏会导致陈旧读取；KCP 重计算若触发跨卡通信则阻塞反向流水。
方案：显式释放 TMEM Map Writes（消除 4 处竞态），通过 recompute_handle 实现无通信本地重计算（94.0 → 61.5 us，1.53x），前向 Workspace 从 384 MB 降至 224 MB（-41.67%）。

Scenario B · SGLang DSv4.1 EPLB Glue Removal & vLLM MI355X TP8 Mono Decode (#47304 / #64101)

问题：EPLB 模拟路由逐层执行 Python/Tensor 胶水映射损耗 48.0 us/层；MI355X TP8 分离算子解码受限于小微批启动开销。
方案：移除 EPLB 逐层胶水（48.0 → 19.5 us，2.46x）；MI355X 启用 DSv4.1 TP8 Mono Decode 将延迟从 14.8 ms 降至 9.6 ms（1.54x）。

Scenario C · Megatron MIMO CP=4 & NIXL CPU Proxy Worker Runtime (#7758 / #2223)

问题：多模态 MIMO 长序列在 CP=1 下占用 18.4 GB 激活；单线程 NIXL Device Proxy 在高频小块传输下仅达 145 Kops/s。
方案：MIMO 接入 CP=4 切分视觉+文本序列（18.4 → 4.9 GB，-73.37%）；NIXL 多工作线程轮询 Proxy Channel 达 510 Kops/s（3.52x）。

架构师结论：训练重计算与设备代理传输的核心优化在于“消除跨卡/跨线程同步瓶颈”——用本地确定性句柄替代重计算通信，用独立控制器/工作池剥离主路径锁竞争。
