• Round 3 Training: 512×H100 (64 nodes), 9,000 GB checkpoint every 1,800s.
• Round 4 Serving: 64K (65,536 tok) multi-turn resume, 2.048 GB FP8 KV payload, 12.0 ms delta prefill.
• Target Gate: >99% training goodput; <100 ms resume TTFT.

7 / 7 · MY TAKE GOOD FIT VS NOT FOR & READINESS

Architect Playbook: Separate Training Checkpoint Persistence from Inference KV Memory Tiering

Use this final card during customer architecture reviews to select the right storage and memory tier on the first try.

✅ Good Fit (When to Adopt)

  • Two-Phase Async DCP (Round 3): Any ≥128-GPU training cluster with ≥2× shard size in free Host Pinned DRAM (e.g., ≥512 GB RAM/node for 140.625 GB shards). Cuts GPU stalls to 3.125 s (99.83% goodput).
  • Sync GDS + RDMA FS (Round 3): Host-RAM-constrained training nodes attached to WEKA / Lustre / 3FS over RDMA with nvidia-fs enabled (25.0 s stall).
  • Host Pinned DRAM KV Pool (Round 4): Single-node or sticky-routed 32K–128K multi-turn Agent/Coding serving (52.0 ms resume TTFT, $0.44/1M).
  • Shared RDMA NVMe + GDS KV Pool (Round 4): Multi-node stateless serving or PD-disaggregated clusters sharing a 10–100 TB KV pool via Mooncake / LMCache + NIXL (62.0 ms TTFT, $0.48/1M).

⛔ Not For (Anti-Patterns to Avoid)

  • Monolithic torch.save() on ≥128 GPUs: Gathering 9 TB to Rank 0 and writing synchronously over POSIX freezes the cluster for 225.0 s and wastes $181.8K/mo.
  • Treating GDS as a Filesystem: GDS (cuFile) is a DMA transport layer, not a storage backend—it cannot replace Lustre/WEKA/3FS or fix slow TCP NAS appliances.
  • Mounting Cloud TCP/POSIX NFS for Real-Time KV Offload: At 3.2 GB/s, loading 2.048 GB KV takes 640.0 ms (total TTFT 652.0 ms), yielding only a 1.20× gain over recomputation.
  • 4 KB Unbatched KV Page Transfers: Small uncoalesced blocks destroy NVMe and RDMA throughput; always batch KV transfers into ≥2 MB blocks (64–256 tokens).
