# 研究框架：从实现到架构

## 目标与路线

研究对象不是独立产品，而是完成 AI 工作负载的系统。每个结论沿以下路径形成：

**需求/SLO → 张量与状态 → 数据/计算路径 → 组件实现 → 性能与容量模型 → 可复核证据 → 架构取舍。**

系统基础深挖和最新成果跟踪并行进行；热点不能替代先修。范围覆盖 [全栈地图](stack-map.md)，GPU/HBM/Network 优先。厂商技术栈作为实现样例，NVIDIA/CUDA 与 AMD/ROCm 对照；不预设某家云或 GPU 永远最优。

## 三种证据，七种登记状态

| 证据范围 | 登记状态 | 可以支持什么 |
|---|---|---|
| 官方公告 | `announcement` | 宣布了什么；不能支持交付、兼容或实测性能 |
| 已读规范/官方接口契约 | `specification` | 实际读取章节中的语义；不能自动证明硬件实现 |
| 固定源码静态阅读 | `implementation` | 所读实现路径；不是运行或生产验证 |
| 作者公布实验 | `author-benchmark` | 作者在指定环境下的结果；不能当成本项目重测 |
| 原创算术/CPU 模型 | `own-offline` | 公式、输入和程序的结果；不是设备性能 |
| 自己的硬件运行 | `own-hardware` | 指定硬件/软件/数据和计时契约下的结果 |
| 未核验 | `unverified` | 待验证问题，不能作为已成立结论 |

用户已掌握是独立维度，不由代理文章或证据状态自动推断。当前没有 `own-hardware` 结果。

## 组件深挖契约

每篇使用 [组件模板](../templates/component.md)，必须给出问题、先修、实现路径、单位/假设、对比、证据边界、架构影响、失败模式、自测与后续问题。无法读取的必要材料阻塞对应结论；不能以标题和通用知识补全“实现已分析”。

GPU 路径关注：

`算子 → 形状/布局 → 框架/编译器 → 库或 kernel → SM/寄存器/共享内存 → L2/HBM`。

分布式路径关注：

`并行布局 → collective/专家交换 → 通信库 → transport/verbs → NIC/内存注册 → 交换拓扑/拥塞 → 同步与恢复`。

每次都问“发生了多少计算、移动了多少数据、谁等待谁、失败时谁恢复”，而不只记录利用率。

## 性能与比较契约

- 固定模型/data revision、batch、输入/输出长度、质量目标、精度、硬件、driver/runtime、并行布局与拓扑。
- 明确计算的是峰值、模型上界、作者结果还是自己的测量；限定适用场景。
- GB/GiB、Gb/s/GB/s、单方向/双向、单链路/设备聚合、稠密/稀疏算力不得混用。
- 推理报告 TTFT、TPOT/ITL、分位数、质量门槛和 SLO-goodput；训练报告有效工作、扩展效率和 checkpoint/恢复影响。
- GPU utilization 不等于 Tensor Core utilization，不等于 MFU；MFU 分母必须与精度、稠密/稀疏及硬件匹配。
- 使用基线、变量/不变量、重复、预热、计时边界和失败分母；没有这些条件的数字不进入产品排行榜。

## 最新技术如何改变架构

每条趋势要回答：旧瓶颈、机制变化、实际证据、相反证据、成熟度、采用门槛。规范发布、源码可用、产品交付和生产表现分别记录；不将多篇转载算成多份独立证据。

首次扫描不声称覆盖全部论文/市场。索引和搜索摘要只用作发现线索；论文/标准全文未读，必须保留相应缺口。
