37B 激活参数能省计算，不能把 671B 权重变没37B active parameters save compute, not 671B weight storage

水位线 1：放得下Bound 1: fit

总权重 + KV Cache + 激活、CUDA Graph、通信缓冲与碎片。先做聚合下界，再核对最忙 rank。Total weights + KV + activations, CUDA graphs, communication buffers and fragmentation. Start with an aggregate floor, then check the busiest rank.

水位线 2：吐得快Bound 2: decode

低 batch Decode 常受内存带宽限制，但 batch 放大后也会转为算力或通信瓶颈。MoE 批内专家并集会增加实际权重流量。Low-batch decode is often bandwidth-bound; larger batches can become compute/communication-bound. MoE's batch expert union increases weight traffic.

水位线 3：首字快Bound 3: prefill

Prefill 要在扣除排队、网关与交接后的 TTFT 预算内完成。长上下文注意力有近似二次项。Prefill must finish within TTFT after queue, gateway and handoff reserves. Long-context attention contributes an approximate quadratic term.

M_w [GB] = (total_params_B + optional_MTP_B) × weight_bytes × (1+metadata_fraction)
M_KV [B] = 2×layers×KV_heads×head_dim×S×B×KV_bytes [MHA / GQA]
M_MLA [B] = layers×(latent_rank+RoPE_dim)×S×B×KV_bytes [compressed cache]
N_mem ≥ ceil((M_w + M_KV_GB) / (GPU_GB×safe_fraction − runtime_GB_per_GPU))

MHA 有一份每个 query head 对应的 K/V；GQA 让多个 query head 共享 KV head。MLA 存压缩 latent 与 RoPE key，不能把 128 个 attention head 直接代入标准公式。DeepSeek 默认每 Token BF16 KV = 61×(512+64)×2 = 70,272 B。MHA has K/V per query head; GQA shares fewer KV heads across query heads. MLA stores compressed latent and RoPE key, not 128 standard K/V heads. DeepSeek's modeled BF16 KV/token = 61×(512+64)×2 = 70,272 B.

单 Token 带宽下界不能预测大 batch MoE 的速度A single-token bandwidth bound cannot predict large-batch MoE speed

TPOT_weight_floor_ms ≈ active_weight_GB / (N_GPU×BW_GBps×MBU) × 1000
Uniform expert union = E×[1−(1−k/E)^B]
shared_params = (active_params−total_params×k/E)/(1−k/E)
batch_active_params = shared_params + routed_params×[1−(1−k/E)^B]
Prefill_FLOPs ≈ 2×active_params×S×B_prefill + 2×layers×hidden×S²×B_prefill
TTFT_compute_floor = Prefill_FLOPs / (N_GPU×dense_BF16_FLOPs×MFU)

37B 激活只描述每 Token。32 个不同请求可能触发大量不同专家，不能仍假设整个 batch 只读 37B。沙盘给出「单 Token 乐观下界」和「均匀路由批内并集场景」两条读权重估算，并额外显示读全 KV 的时间；均匀路由只是解释模型，不是现实路由预测。37B active describes one token. A batch of 32 distinct requests can activate many experts; the batch need not read only 37B. The workbench shows a single-token optimistic bound and a uniform-routing batch-union scenario, plus a full-KV read estimate. Uniform routing explains the effect; it does not predict real routing.

Prefill 使用 dense BF16 标称 FLOPs×假设 MFU，而不是把权重量化自动当成算力翻倍。MoE 通信、内核效率、量化转换、attention 具体实现与首 Token decode 均可能让实际 TTFT 更高。Prefill uses nominal dense BF16 FLOPs×assumed MFU, not an automatic compute doubling from quantized storage. MoE communication, kernels, dequantization, attention implementation and first-token decode can all increase real TTFT.

沙盘保守地把完整驻留上下文 S 也作为一次完整 Prefill 的输入长度。B_prefill 是同时做完整 Prefill 的请求数，与驻留/decode 请求数 B 分开。实际 Prompt 比 S 短时，应把 Prefill 输入长度与 KV 峰值上下文分别测量，而不是把本例当预测。The workbench conservatively uses full resident context S as the input length of a full prefill. B_prefill counts simultaneous full-prefill requests separately from resident/decode B. When actual prompts are shorter, measure prefill length and peak KV context separately; this example is not a prediction.

70B FP8 权重约 70.6 GB；32×8K BF16 KV 另需 85.90 GB70B FP8 weights are about 70.6 GB; 32×8K BF16 KV adds 85.90 GB

Llama 70B GQA: 2×80×8×128×2 = 327,680 B/token
KV at S=8,192, B=32: 327,680×8,192×32 = 85,899,345,920 B = 85.90 GB = 80 GiB
Weights with 5% allowance: 70.6×1.05 = 74.13 GB
H200 safe payload/GPU: 141×0.85−3 = 116.85 GB
Memory floor: ceil((74.13+85.90)/116.85) = 2 GPUs

上例只证明理想聚合内存至少 2 卡，不证明 2 卡必达 SLA。BF16 权重将权重项翻倍；FP8 KV 将 KV 项减半；长输出、KV 复制、专家冗余和额外 MTP 要独立计入。GB=10⁹ B，GiB=2³⁰ B；这里故意展示两者。This only proves an ideal aggregate floor of 2 GPUs, not that 2 meet the SLO. BF16 doubles the weight term; FP8 KV halves the KV term. Long outputs, KV replication, expert redundancy and extra MTP are separate. GB=10⁹ B and GiB=2³⁰ B; both are shown deliberately.

模型名、存储精度和 GPU 商品名都不是完整配置Model names, storage dtype and GPU branding are not full configurations

DeepSeek 能用激活 37B 来算加载显存吗？Can DeepSeek loaded memory use its 37B active size?

不能。GPU 常驻全模型的目标下，用 671B 总参数算主权重；加载额外 MTP 再加 14B。CPU/NVMe offload 是另一种部署边界，吞吐必须把搬运和 CPU 计算计入。No. For a GPU-resident full model, use 671B main weights and add 14B if MTP is loaded. CPU/NVMe offload is a different deployment boundary; include transfers and CPU compute.

MLA 是否让所有实现的 KV 都自动只占 35 KB/token？Does MLA guarantee 35 KB/token in every implementation?

不保证。61×576×1=35,136 B/token 只在压缩表示且所有分量按 1 B 存储时成立。RoPE、scale、padding、TP 复制、MTP state 与 kernel 支持都会改变真实占用。No. 61×576×1=35,136 B/token requires compressed cache and one byte for every component. RoPE dtype, scales, padding, TP replication, MTP state and kernels can change occupancy.

80–85% 水位是 vLLM 当前默认值吗？Is an 80–85% watermark vLLM's current default?

不是。这是可调的架构规划余量，不是引擎默认宣称。运行时测量/内存策略在版本之间变化，必须记录实际 flags、启动 profile、图捕获与稳态峰值。No. It is an adjustable architectural planning margin, not an engine default claim. Runtime profiling and memory policies change by version; record actual flags, startup profile, graph capture and steady-state peak.
