Prefill 和 Decode 混部会争资源，不只是争 FLOPsColocated prefill and decode compete for more than FLOPs

Prefill 一次处理大量输入 Token，矩阵计算往往更密集；低 batch Decode 每步生成一枚 Token，反复读权重和 KV，通常更吃带宽。二者还竞争 kernel 调度、SM、缓存、显存容量与通信。边界并不绝对：短 Prefill 也可能受带宽/启动开销限制，大 batch Decode 也可能算力受限。Prefill processes many input tokens with denser matrix work; low-batch decode generates one token per step and repeatedly reads weights and KV, often stressing bandwidth. They also compete for kernel scheduling, SMs, caches, capacity and communication. Short prefill can be launch/bandwidth-bound; large-batch decode can be compute-bound.

Chunked Prefill 把长输入拆小，并优先调度 Decode，降低单次阻塞，但资源仍在共池。PD 用独立资源池隔离这类干扰，代价是第二份模型驻留、KV 交接、路由与两池配比。不要把 P/D isolation 误译成「系统没有抖动」。Chunking splits long inputs and prioritizes decode, reducing individual stalls while keeping shared resources. PD isolates this interference with separate pools but adds duplicate model residency, KV handoff, routing and pool-ratio management. Isolation does not mean a jitter-free system.

图中的 P99 从哪里来？Where do the plotted P99 values come from?

每个上下文点生成 200 个确定性 ITL 样本：5% 注入 Prefill 干扰，共池注入整段、chunk 注入 min(S,chunk)，PD 注入可调残留干扰。用 nearest-rank 取 P99。它是可复算教学模拟，不是硬件 P99，也不预测网络过载。Each context point generates 200 deterministic ITLs: 5% inject full-prefill, min(S,chunk) or adjustable residual PD interference. Nearest-rank computes P99. This is reproducible teaching simulation, not hardware P99 or an overload predictor.

PD 交接时间能直接加到每个 decode Token 的 ITL 吗？Should handoff time be added to every decode token's ITL?

通常不能。交接主要是请求开始/首字路径的一次成本；Decode 中后续抖动由 D 池排队、网络争用和运行时决定。图把交接时间与尾部模拟分开，避免重复计费。Usually no. Handoff is primarily a one-time request-start/first-token cost. Later decode jitter depends on D-pool scheduling, contention and runtime. Handoff and ITL simulation are shown separately.
