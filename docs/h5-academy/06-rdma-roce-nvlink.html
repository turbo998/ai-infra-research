PCIe Gen3/4/5 one-way encoded GB/s = GT/s_per_lane×lanes×(128/130)/8
Network payload = port_Gb/s/8×payload_efficiency
Node path bound = min(active_ports×port_payload, GPU_endpoint_PCIe, NIC_card_PCIe,
crossed_shared_links, allocated_fabric)
Striped transfer lower bound ms = payload_MB / path_GBps

PCIe Gen5 x16编码后单向约63.02 GB/s；再按本例85%payload比例为53.56。即使800G端口线速100 GB/s、网络效率80%为80，单PCIe端点仍可能先卡住。双端口NIC也可能共用一条PCIe链路，不能把“端口数”当“NIC卡数”。PCIe Gen5 x16 gives about 63.02 GB/s one-way after coding, or 53.56 at the example 85% payload fraction. An 800G port is 100 GB/s line rate and 80 at 80% efficiency, yet one PCIe endpoint can bottleneck first. Dual-port NICs may share a PCIe link: port count is not NIC-card count.

默认8个GPU端点、8张单端口400G NIC，网络payload320 GB/s；共享路径300、分配fabric240，因此上界240 GB/s。1024 MB完全条带传输下界约4.27 ms；若只有1个GPU端点参与，上界可降至53.56，不能把8张NIC带宽全给一张GPU。Default eight GPU endpoints and eight single-port 400G NICs provide 320 GB/s network payload, with shared-path 300 and allocated-fabric 240: bound 240 GB/s. A fully striped 1024 MB transfer has about 4.27 ms lower bound. With only one GPU endpoint, it can fall to 53.56; eight NICs do not bypass one GPU endpoint.

这是单向路径预算，不是实际吞吐或P99；输入需要取两端实际链路与分配的较小值。GPU选择仅用于NVLink规格对照，PCIe代际/lanes独立填真实协商值，不按型号猜。只有真正经过共享链路才纳入约束；PCIe6/7的PAM4/FLIT不适用此128b/130b公式。各沙盘输入独立，比较前对齐。This is a one-way path budget, not measured throughput/P99. Use smaller actual endpoint links/allocations. GPU selection only supplies NVLink reference; enter actual negotiated PCIe generation/lanes independently, not from branding. Include shared links only if crossed. PCIe6/7 PAM4/FLIT does not use this128b/130b formula. Align independent workbench inputs before comparing.

8 ranks 的 AllReduce：busbw=1.75×algbw，不是压缩收益At 8 ranks, AllReduce busbw=1.75×algbw, not compression

algbw [GB/s] = effective_total_S_MB / time_ms
API-count mode: AllGather(sendcount), ReduceScatter(recvcount), fixed AllToAll(per-peer count)
need total S = count×dtype_bytes×n; AllReduce/Broadcast/Reduce/SendRecv do not multiply n
AllReduce busbw = algbw×2(n−1)/n
AllGather / ReduceScatter / fixed AllToAll busbw = algbw×(n−1)/n

默认消息 1,000 MB、20 ms：algbw=50 GB/s；8 ranks AllReduce busbw=87.5 GB/s。busbw 是标准化通信指标，不是「网络凭空超出线速」。AllGather/ReduceScatter 的 S 要用总数组大小，不是每 rank 的单块。Default 1,000 MB in 20 ms: algbw=50 GB/s; 8-rank AllReduce busbw=87.5 GB/s. Bus bandwidth is a normalized collective metric, not magical wire speed. For AllGather/ReduceScatter, S is the total array, not one rank's shard.

单端口网络效率预算不能直接套到所有 GPU 集合通信：操作可能走 NVLink、多个 NIC、PCIe 或混合路径。若指标超过选定预算，先核对路径、方向、总消息定义和轨数，而不是自动宣告测量错误。One-port network budgets do not apply automatically to every GPU collective; paths may use NVLink, multiple NICs, PCIe or a mix. If a metric exceeds the selected budget, check path, direction, size definition and rails before declaring an error.
API count指本操作实际使用的count×dtype字节，不是命令行请求的名义大小；NCCL-tests可按对齐取整。AllToAllv的可变分发需看最大send/recv计数，本转换器只覆盖固定AllToAll，不能拿平均专家流量推busbw。API count means actual operation count×dtype bytes, not nominal command-line requested size; NCCL-tests can round for alignment. Variable AllToAllv uses maximum send/recv counts; this converter covers fixed AllToAll and cannot infer busbw from mean expert traffic.

ECN 是提前减速，PFC 是逐跳急刹，DCQCN 是端点反馈控制ECN signals early, PFC brakes a hop, DCQCN controls the sender

传统 lossless RoCE 基线：交换机队列到 ECN 区间先标记 CE；接收端 RNIC 产生 CNP；发送端 RNIC 的 DCQCN 降速，再逐步恢复。如果队列继续逼近溢出，PFC 按 priority 对上游链路发 pause；低于 Xon 再恢复。标记/减速不是丢包；PFC 不是端到端拥塞控制。Classic lossless-RoCE baseline: the switch marks CE as queues enter the ECN range; the receiver RNIC emits CNP; sender RNIC DCQCN reduces rate then recovers. If queues keep nearing overflow, PFC pauses an upstream priority on a hop, resuming below Xon. Marking/rate reduction is not packet loss; PFC is not end-to-end congestion control.

阈值滑块是概念图，不是厂商配置。ECN/PFC/DCQCN 不是所有现代以太网 fabric 的唯一有效组合；替代拥塞控制、receiver credits 与可承受丢包的实现要按协议和负载验证。避免 PFC 死锁、head-of-line blocking，并启用可验证的 watchdog 与遥测。Threshold sliders illustrate concepts, not vendor configuration. ECN/PFC/DCQCN is not the only valid modern fabric design; alternative congestion control, receiver credits and loss-tolerant implementations need protocol/workload validation. Address PFC deadlock/HOL blocking with verified watchdogs and telemetry.

A16MB teaching queue keeps3.2MB after80% Xoff. Increase response to100µs or use800G and headroom rises sharply: copying an'80% pause' threshold is insufficient. 多轨拓扑要匹配 GPU↔NIC 亲和与集合通信映射Rail topology must match GPU↔NIC affinity and collective mapping

Per-rail time floor = assigned_payload_GB / effective_rail_GBps
Fabric time floor = total_payload_GB / allocated_fabric_GBps
Completion floor = max(per-rail floors, fabric floor), only if every assigned flow has a live path

8个GPU各发1GB、4条400G rail、80%效率：均衡映射每rail2GB，下界50ms；全挤到一rail变成200ms。失去一rail后若玩具重映射到3条存活rail，负载3/3/2GB，下界75ms而不是自动“3×40GB/s”满载。若不重映射，完整集合通信无法完成，必须显示阻塞而不是成功吞吐。Eight GPUs send 1 GB each over four 400G rails at 80% efficiency: balanced 2 GB/rail gives a 50 ms floor; one-rail collision gives 200 ms. Toy remapping after one failure yields 3/3/2 GB and 75 ms, not automatic full 3×40 GB/s. Without remapping, the whole collective cannot complete: report blocked flows, not successful throughput.

这是出站payload映射教学，不模拟NCCL图搜索、ECMP/DLB、SHARP、对端拥塞或故障恢复耗时。热点GPU、PCIe亲和与接收端也可改变结果。RA的rail-aligned拓扑是物理基础，不保证每个任务自动充分利用；真实all-to-all和KV共载需测。This outgoing-payload mapping exercise does not simulate NCCL graph search, ECMP/DLB, SHARP, receiver congestion or recovery time. Hot GPUs, PCIe affinity and receivers change outcomes. Rail-aligned RA topology is a physical foundation, not automatic full utilization; test actual all-to-all plus KV traffic.

RDMA 是否完全不使用 CPU？Does RDMA avoid the CPU entirely?

数据面可以绕过 host staging，但连接建立、内存注册、页固定、队列配置、控制与错误处理仍需要 CPU/驱动。GPU-initiated 通信也不取消全部控制平面。Payload can bypass host staging, but connection setup, registration, pinning, queues, control and errors still involve CPU/drivers. GPU-initiated communication does not remove all control-plane work.

NCCL busbw 可以跨不同 rank 数直接比较吗？Can NCCL busbw be compared across rank counts?

可以作为标准化参考，但必须同操作、消息大小定义、路径、拓扑、dtype、warmup、迭代窗口与错误状态；小消息看 latency，大消息看带宽，并用实际训练/推理负载复验。It is a normalized reference, but compare the same operation, size scope, path, topology, dtype, warmup, iterations and error state. Use latency for small messages, bandwidth for large ones, then verify real workloads.
