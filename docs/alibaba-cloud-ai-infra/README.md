# 阿里云 AI Infra 全栈架构深度测评报告：从平头哥“算存网”芯片到灵骏、PAI 与百炼平台

> **Executive Summary / 核心概览**：本报告从 AI Infra 架构师视角系统拆解阿里云 **“通-云-哥”（通义大模型 × 阿里云算存网底座 × 平头哥自研芯片）L0–L3 全栈垂直整合架构**，涵盖平头哥真武 PPU 四代演进（810E→V900）、磐久 AL128 超节点五芯数据通路、HPN 7.0 双上联×多轨×双平面网络（SIGCOMM 2024，算力利用率 `+14.9%`）、PAI 灵骏潮汐混部与百炼四大算力模式选型矩阵。


- **研究日期**：2026-10-14
- **研究定位**：AI Infrastructure 架构师视角全栈产品布局、架构机理、代际对比与选型测评（不含实机跑分 Benchmark）
- **覆盖范围**：
  - **L0 芯片与硬件层（平头哥 T-Head）**：AI 加速卡 PPU（含光 800 → 真武 810E → 真武 M890 → 真武 V900 → 真武 J900）、服务器 CPU（倚天 710 / 720 / 730 / 750、玄铁 RISC-V）、片间互联交换芯片（ICN Switch 1.0）、AI 智能网卡（磐脉 920）、企业级 SSD 主控芯片（镇岳 510）
  - **L1 算存网底座层（阿里云基础设施）**：磐久 AL128 超节点服务器、CIPU 云基础设施处理器、HPN 7.0 高性能网络（双上联 + 多轨 + 双平面）、Solar-RDMA / eRDMA、ACCL 集合通信库、CPFS 并行文件系统
  - **L1.5 / L2 智算与 AI 工程平台层**：灵骏智算平台（PAI-Lingjun）、人工智能平台 PAI（语音常称“Pi平台”，含 PAI-DLC、PAI-EAS、PAI-DSW、训推一体父子配额抢占、LLM 智能路由、MoE EP+PD 分离）

## 0. 一页纸架构师核心结论（Executive Summary）

从 AI Infra 架构师视角审视，阿里云是目前国内极少数完成 **“通-云-哥”（通义大模型 + 阿里云算存网底座 + 平头哥自研芯片）L0–L3 全栈垂直整合** 的云厂商，其架构演进路径对标 **AWS（Annapurna Trainium/Graviton/Nitro + UltraCluster + SageMaker + Bedrock）** 与 **Google Cloud（TPU + Jupiter/ICI + Vertex AI）**：

1. **平头哥 PPU 的核心架构策略是“以高显存容量 + 高片间带宽 + 超节点 Scale-Up 统一编址，对冲单芯片先进制程裸算力约束”**：
   - 从 **真武 810E（96GB HBM2e，700 GB/s 片间互联）** 到 **真武 M890（144GB HBM3，800 GB/s 8×ICN 互联，3× 810E 性能）**，再到 2026 年 9 月云栖大会发布的 **真武 V900（216GB HBM，1200 GB/s 片间互联，3× M890 性能，2027Q1 量产）**，平头哥每一代均保持 **+50% HBM 显存容量与 +50% 级互联带宽跃升**，并原生支持 **FP8 / FP4** 低精度算子。
   - 这种设计并非单纯追求单卡稠密 FP16 峰值算力，而是精准卡位 **万亿参数稀疏 MoE 模型（如 Qwen3.5/3.8、DeepSeek-V3/V4、Kimi K3）的权重常驻** 与 **Agent 时代百万 Token 长上下文 KV Cache 访存瓶颈（Decode 阶段 Memory-bound）**。
2. **“算-存-网”五芯协同构筑了磐久 AL128 超节点闭环**：
   - 平头哥不仅做 PPU，还通过 **ICN Switch 1.0（25.6 Tbps，<150ns 延迟，支持 Load/Store 内存语义与统一编址）**、**倚天 710/750 Arm 服务器 CPU（750 原生支持 ICN 协议直连 PPU）**、**磐脉 920 400G 智能网卡（内置 PCIe Switch 实现算-网-存数据直通）** 以及 **镇岳 510 PCIe 5.0 SSD 主控（3400K IOPS、4μs 时延、ZNS+QLC 支撑 KV Cache 卸载与秒级 Checkpoint）**，在单机柜内构建了最高 64/128 卡无损 Scale-Up 域（灵骏 `GP9A` 超节点实例）。
3. **HPN 7.0 + Solar-RDMA 是阿里云在十万卡级 Scale-Out 网络上的最大工程壁垒**：
   - 针对传统 RoCEv2 网络在大模型低熵大象流下的 ECMP 哈希极化、ToR 单点故障和 PFC 死锁风暴，阿里云 **HPN 7.0（SIGCOMM 2024）** 采用 **“双上联（Dual Uplink）+ 多轨（Multi-Rail）+ 双平面（Dual Plane）”** 架构，基于 51.2 Tbps 交换芯片以两层无收敛 Clos 容纳 15,000+ 张加速卡；配合 CIPU 卸载的 **Solar-RDMA（多路径包喷洒 + HPCC 精准拥塞控制）** 与 **ACCL 集合通信库**，将大模型分布式训练有效算力利用率提升了 **14.9%**。
4. **灵骏、PAI（“Pi平台”）与百炼形成清晰的 L1.5 / L2 / L3 三层漏斗，工程化深度极高**：
   - **灵骏（PAI-Lingjun）** 解决“超节点裸金属 + HPN 高速网络域（`hz`）+ CPFS 并行存储 + 硬件故障自愈”；
   - **PAI（Platform for AI）** 解决“异构集群调度与分布式训推工程”——其 **训推一体父子配额树（白天 EAS 在线推理高优抢占、夜间 DLC 离线训练波谷回填）**、**AIMaster + EasyCKPT 容错续训**、**EAS LLM 智能路由（Prefix-Cache 路由降低 23%~25% TTFT）** 与 **MoE EP+PD 分离一键模板** 均直击企业 AI Infra 痛点；
   - **百炼（Model Studio）** 解决“开箱即用 MaaS 与精细化算力消费”——通过 **Token 按量 → PTU（预置吞吐 + 前缀缓存 8%~25% 折算折扣）→ DTU（独占吞吐）→ MU（模型单元，直接暴露 PD 分离规格）** 四级阶梯，让架构师在延迟确定性、数据隔离与 TCO 之间精准切分。
5. **架构师必须正视的核心短板与风险**：
   - **软件栈生态**：平头哥 **SAIL 软件栈** 对 通义千问（Qwen）、DeepSeek、Kimi 等主流大模型完成了深度适配，但面对高度自定义的 CUDA C++ / PTX 内核、冷门科学计算算子或非标科研模型，仍存在迁移与算子重写成本；
   - **规格透明度**：平头哥官方未在公开产品手册中披露真武 810E/M890/V900 各精度档位的绝对峰值 TFLOPS（仅披露代际 3× 倍率及显存/带宽参数），企业在混合云/跨芯片立项时必须在真实 Workload 上做端到端实测验证；
   - **商务与锁定**：灵骏旗舰超节点（如 `GP9A`）与百炼 DTU 存在地域集中、白名单邀测及包月退订按已用部分 `1.2×` 系数结算等商务约束；深度使用 `ICN + Solar-RDMA + ACCL + BladeLLM` 带来显著的阿里云技术栈绑定。

## 2. L0 平头哥（T-Head）AI 芯片矩阵深度剖析：GPU/PPU、CPU、交换与存储芯片

### 2.1 AI 加速卡（PPU）演进与代际性能特点对比（含光 800 → 真武 810E → 真武 M890 → 真武 V900 → 真武 J900）

#### 2.1.1 为什么平头哥将大模型加速卡命名为 PPU（Parallel Processing Unit）？

在阿里平头哥的芯片体系中，云端 AI 加速芯片经历了从 **第一代专用推理 ASIC（含光 800，2019 年发布，12nm，825 TOPS INT8）** 向 **通用并行处理器 PPU（Parallel Processing Unit，真武系列）** 的代际跨越：
- **架构演进动因**：含光 800 针对 ResNet/CNN 等静态计算图视觉推理做极致硬化，虽然能效比极高，但缺乏支撑 Transformer、MoE 动态路由、强化学习（RL）后训练与复杂算子快速演进的通用可编程性。
- **PPU 的架构实质**：真武系列 PPU 本质上是 **面向大模型训练与推理一体化的类 GPGPU / 通用张量并行处理器架构**，去除了传统图形渲染管线（光栅化、纹理贴图单元），将芯片面积集中投入到 **高密张量核心（支持 FP32/BF16/FP16/FP8/FP4）、大容量 HBM 显存控制器、片上高带宽 NoC 以及 8 通道独立 ICN（InterChip Network）片间互联接口**，同时保留了硬件编解码引擎（VPU）以支撑多模态视频/视觉理解。

#### 2.1.3 架构师深度拆解：真武 810E（初代 PPU）、M890 与 V900 的性能特点与设计哲学

从 AI Infra 架构师的视角看，平头哥真武系列（特别是主力出货的 **M890** 与新一代 **V900**）并不是简单模仿 NVIDIA H100 的均衡参数表，而是针对 **2025–2027 年大模型架构范式转移** 做了极具针对性的工程取舍：

1. **特点一：激进的 HBM 显存容量阶梯（`96GB → 144GB → 216GB`），直击 MoE 与长上下文痛点**
   - **为什么是 144GB 和 216GB？** 当前主流开源与闭源旗舰模型已全面转向 **MoE（混合专家）架构**（例如 `Qwen3.5-397B-A17B`、`DeepSeek-V3/V4 671B+`、以及参数量突破 2 万亿的 `Qwen3.8` / `Kimi K3`）。MoE 模型的典型特征是**“激活参数小（计算量可控），但总权重参数极其庞大（显存容量刚性受限）”**。
   - 使用 80GB/96GB 显存卡部署 671B~2T 参数模型时，为了装下权重并留出 KV Cache 空间，往往被迫将张量并行（TP）或专家并行（EP）切分到更多机器节点，引发昂贵的跨机网络通信延迟。
   - **真武 M890 的 144GB HBM3**（与 NVIDIA H200 的 141GB 处于同一容量级，比 810E 和 H20 整整多出 48GB）允许单台 8 卡节点提供 **1.15 TB HBM3**，单台 64 卡磐久 AL128 超节点提供 **9.2 TB HBM3**（128 卡达 **18.4 TB**）；而 **真武 V900 的 216GB HBM** 更将单卡显存推升至 H100（80GB）的 **2.7 倍**。这意味着更少的切分粒度、更高的单卡 Batch Size 上限，以及在百万 Token Agent 多轮对话中直接将海量 Prefix KV Cache 驻留在 HBM 内。
2. **特点二：原生 FP8 / FP4 低精度张量加速，弥合单芯片制程与算力鸿沟**
   - 相比初代真武 810E，**真武 M890 与 V900 原生引入了硬件级 FP8 与 FP4 精度支持**（这一特性在国际上直到 NVIDIA Blackwell B200 才全面普及，而国内存量庞大的 H20 与昇腾 910B 均不支持原生 FP4）。
   - 在万亿参数模型的推理（尤其是 Prefill 计算密集阶段与 Decode 权重量化加载阶段）以及 FP8 混合精度预训练中，原生 FP8/FP4 不仅将等效算力翻倍/翻四倍，更将模型权重占用的显存带宽需求直接减半，从而在先进制程受限的客观条件下实现了 **M890 较 810E 达 3 倍、V900 较 M890 再达 3 倍** 的系统级吞吐跃升。
3. **特点三：8 路独立 ICN 端口（M890 800 GB/s → V900 1200 GB/s）+ Load/Store 内存语义超节点**
   - MoE 模型推理（特别是 Decode 阶段开启大 EP 专家并行时）最致命的瓶颈是 **All-to-All 细粒度高频通信**（每次只传输几 KB 到几十 KB 的 Token 隐状态，对通信启动延迟极其敏感）。
   - 真武 M890 在单芯片上集成了 **8 个独立的 ICN（InterChip Network）高速端口**，提供 **800 GB/s** 片间互联带宽（超越 810E 的 700 GB/s），并通过 **ICN Switch 1.0 交换芯片** 将端到端 P2P 延迟压低至 **<150 纳秒**；到 **真武 V900** 代际，片间带宽进一步跃升至 **1,200 GB/s**（超越 Hopper NVLink 4.0 的 900 GB/s），并在超节点内实现了 **原生 Load/Store 内存读写语义与统一内存编址（Unified Memory Addressing）**，使远端 PPU 访问相邻 PPU 显存无需经过繁琐的 RDMA 队列协商，从而在灵骏 `GP9A` 超节点上率先跑通了 **>2 万亿参数大模型（Qwen3.8、Kimi K3）** 的高效训练与推理。
4. **特点四：单芯片集成 64 路 H.265 解码 + 16 路编码，专为原生多模态（VLM / Omni）优化**
   - 在 `Qwen3-VL`、`Qwen3.5-Omni`、具身智能与自动驾驶（如小鹏汽车场景）的多模态训练与在线推理中，视频抽帧解码往往打满宿主机 CPU 并造成 PCIe 传输拥塞。真武 M890 在 PPU 内部直接集成了 **16 路 H.264/H.265 硬件编码与 64 路 H.265 硬件解码器**，让视频流解码后直接在 HBM 显存内送入 Vision Encoder，消除了 CPU-GPU 拷贝开销。

1. **ICN Switch 1.0（片间互联交换芯片）—— 打破单机 8 卡边界的 Scale-Up 核心**：
   - 传统服务器受限于主板拓扑，Scale-Up 域通常停留在单机 8 卡，一旦跨机就必须退化到带宽降级一个数量级的 RDMA 网络。
   - 平头哥自研 **ICN（InterChip Network）协议与 ICN Switch 1.0 交换芯片**，单芯片提供 **25.6 Tbps** 交换容量，端口到端口（P2P）转发延迟 **低于 150 ns**，支持 **Load/Store 内存语义与全超节点统一内存编址**。借此，磐久 AL128 将单机柜 **64 至 128 张真武 M890**（V900 代际扩展至 **1,000 卡**）虚拟化为一个高带宽共享显存池，使 MoE 模型的专家并行（EP）通信完全留在百纳秒级 Scale-Up 域内。
2. **磐脉 920（Panmai 920，2026 年 4 月发布）—— 内置 PCIe Switch 的 400G AI 智能网卡**：
   - 平头哥首款专为 AI 算力集群设计的 400G 智能网卡。其最大的微架构创新是 **在智能网卡芯片内部直接集成了 PCIe Switch**。
   - **架构收益**：在传统服务器中，GPU 与网卡、NVMe SSD 之间的 P2P 通信往往受制于 CPU Root Complex 或外置独立 PCIe Switch 芯片的拓扑跳数。磐脉 920 将 PCIe 交换矩阵与 400Gbps RDMA 引擎合封，使真武 PPU 能够以最短路径直接向网络发送梯度（GPUDirect RDMA 等效）或从本地 NVMe SSD 直接拉取模型权重与 KV Cache（GPUDirect Storage 等效），彻底消除 Host CPU 内存拷贝。
3. **镇岳 510（Zhenyue 510）—— 面向 AI Checkpoint 与 KV Cache 卸载的企业级 PCIe 5.0 SSD 主控**：
   - 采用 12nm 工艺，内置平头哥自研 **玄铁 910 RISC-V 多核处理器（1.6GHz）**，支持 PCIe 5.0 与 16 个 NAND 通道，实测性能达 **3,400K IOPS**、**14 GB/s 顺序读**、**10 GB/s 顺序写**、**4 μs 极低访问延迟**，能效比达 **420K IOPS/W**，软硬件联合纠错实现 **`10^-18` UBER（不可纠正误码率）**。
   - **AI Infra 专属价值**：
     - **万卡训练秒级 Checkpoint 落盘**：配合 PAI-DLC 的 `EasyCKPT` 与 CPFS 并行文件系统，支撑万亿参数模型高频快照写入而不阻塞训练流水线；
     - **Agent 时代的长上下文 KV Cache 存储池（ZNS + QLC）**：镇岳 510 原生支持 **ZNS（分区命名空间）与高密度 QLC 闪存优化**，目前已出货超 **50 万片** 并全面部署于阿里云 EBS、OSS 与 CPFS 中，作为 HBM → Host DRAM 之后的 **第三级微秒级 KV Cache 持久化缓存层**，将长上下文多轮对话的重复 Prefill 算力消耗转化为廉价的极速 SSD 读取。

## 3. L1 阿里云 AI 网络与算力底座架构：磐久超节点、CIPU、HPN 7.0、Solar-RDMA 与 CPFS

如果说平头哥芯片提供了“点”上的算存网原语，那么阿里云基础设施团队则通过 **磐久超节点（Scale-Up）+ HPN 7.0（Scale-Out）+ CIPU/Solar-RDMA（传输卸载）+ CPFS（并行存储）** 将十万张加速卡编织成了一台“超级计算机”。

### 3.1 Scale-Up 域：磐久 AL128 超节点服务器与灵骏 GP9A 实例

- **高密正交无线缆（Cableless）工程设计**：磐久 AL128 采用正交背板无线缆直连设计、全液冷散热与集中式高压直流供电，在单机柜内高密度集成 **64 至 128 张平头哥真武 PPU**、倚天 Arm CPU、ICN Switch 交换模组、磐脉智能网卡与镇岳 SSD。
- **云端产品化形态（灵骏 GP9A 超节点实例）**：阿里云已将磐久 AL128 超节点封装为灵骏智算平台的 **`GP9A` 超节点实例**，并成为国内首个成功跑通 **2 万亿参数以上大模型（如通义千问 Qwen3.8、月之暗面 Kimi K3）** 的国产全自研超节点。

### 3.2 Scale-Out 域：HPN 7.0（SIGCOMM 2024）高性能智算网络架构

![阿里云 HPN 7.0 双上联 × 多轨 × 双平面网络架构与性能收益对比](assets/04-hpn7-dual-plane-topology.svg)

在大模型分布式训练与跨节点推理中，网络流量呈现出与传统云数据中心截然不同的特征：**流数量极少（低熵）、单流带宽极大（大象流）、全节点周期性同步突发（AllReduce / All-to-All Incast）**。传统 RoCEv2 网络在此场景下面临三大顽疾：
1. **ECMP 哈希极化（Hash Polarization）**：由于并发流数量少，基于五元组哈希的 ECMP 极易将多条 200G/400G 大象流哈希到同一条上行链路，导致局部链路拥塞丢包而其余链路空闲，实测有效带宽往往跌至理论值的 50% 以下；
2. **ToR 交换机单点故障敏感**：传统单网卡单上联架构下，一旦某台 ToR（架顶交换机）重启或光模块闪断，挂接其下的整机柜 GPU 全部掉线，触发整个千卡/万卡训练作业回滚重跑；
3. **PFC（优先流量控制）死锁与头阻风暴**：无损以太网依赖 PFC 反压，单点拥塞会像多米诺骨牌一样向全网扩散，拖慢同集群其他租户作业。

为此，阿里云研发并在 **ACM SIGCOMM 2024** 顶会上发表了新一代高性能网络架构 **HPN 7.0（High Performance Network 7.0）**，通过三大拓扑创新彻底重构了万卡级 RoCE 网络：

```text
           [ 阿里云 HPN 7.0: 双平面 (Dual Plane) + 多轨 (Multi-Rail) + 双上联 (Dual Uplink) ]

   +----------------------------------------+         +----------------------------------------+
   |       Core / Spine 交换层 (平面 A)     |         |       Core / Spine 交换层 (平面 B)     |
   |  (基于 51.2 Tbps 单芯片以太网交换机)   |         |  (基于 51.2 Tbps 单芯片以太网交换机)   |
   +----------------------------------------+         +----------------------------------------+
            ^                      ^                           ^                      ^
            |                      |     两层无收敛 Clos       |                      |
            |                      |   单集群容纳 15,000+ 卡   |                      |
            v                      v                           v                      v
   +-----------------+    +-----------------+         +-----------------+    +-----------------+
   | ToR A1 (Rail k) |    | ToR A2 (Rail k) |         | ToR B1 (Rail k) |    | ToR B2 (Rail k) |
   +-----------------+    +-----------------+         +-----------------+    +-----------------+
            ^                      ^                           ^                      ^
            |   双上联 (Dual Uplink) + 双平面 (Dual Plane) 分流                        |
            +-----------+----------+---------------------------+----------------------+
                        |                                      |
                        | 端口聚合分流 (2 x 200G = 400G)       |
                        +------------------+-------------------+
                                           |
                                 +-------------------+
                                 | 400G 智能网卡 (k) |  <-- 单机 8 张 400G 网卡分属 8 条独立轨道 (Multi-Rail)
                                 +-------------------+
                                           |
                                 +-------------------+
                                 |   GPU / 真武 PPU  |  <-- 机内通过 NVLink / ICN Switch 全互联
                                 +-------------------+
```

1. **创新一：双上联（Dual Uplink）—— 彻底消除 ToR 单点故障**：
   - 每张 400G 网卡通过一分二线缆（2×200G）同时连接两台独立的 ToR 交换机。任一 ToR 交换机或单根光纤发生故障，网卡流量在硬件层无缝切至另一台 ToR，训练作业不断连、不回滚。
2. **创新二：双平面（Dual Plane）—— 物理消除 ECMP 哈希极化**：
   - 整个集群在物理上划分为两个完全独立、对称的网络平面（Plane A 与 Plane B）。单张网卡的两个 200G 端口分别接入两个平面，配合轨内端口聚合（Port Bonding），使大象流在发包端即被均匀切分到两个物理平面，从根源上消除了跨轨哈希冲突。
3. **创新三：多轨互联（Multi-Rail）+ 51.2T 交换芯片两层无收敛 Clos**：
   - 单台计算节点的 8 张 400G 网卡分别接入 8 组独立的 Rail ToR（同号卡优先走同一组 ToR 实现最短一跳通信，跨号卡通过机内 NVLink/ICN Switch 转发）。
   - 采用 **51.2 Tbps 单芯片高密以太网交换机**，仅需 **两层（Leaf-Spine）无收敛（1:1 Non-oversubscribed）Clos 架构即可单集群接入超过 15,000 张 GPU/PPU**（相比传统三层 Clos 减少一层交换机跳数与光模块成本，扩展三层可达十万卡级）。

### 3.3 传输协议栈与通信库：CIPU、Solar-RDMA、eRDMA 与 ACCL

在 HPN 7.0 物理拓扑之上，阿里云构建了从芯片卸载到集合通信的完整协议栈：
- **CIPU（Cloud Infrastructure Processing Unit，云基础设施处理器）**：阿里云“飞天+CIPU”架构的核心管控与数据面卸载芯片，将计算虚拟化、EBS/CPFS 存储 I/O 以及 RDMA 网络协议栈全部从宿主机 CPU 卸载到专用硬件。
- **Solar-RDMA + HPCC（高精度拥塞控制）**：
  - 阿里云自研的增强型 RDMA 传输协议，运行于 CIPU / 智能网卡硬件之上。
  - 支持 **多路径数据包喷洒（Multi-path Packet Spraying）** 与乱序重排硬件容忍：将单条 RDMA 大象流按包/信元粒度打散到 HPN 7.0 的多条等价路径上，彻底榨干双平面多轨的每一分物理带宽；
  - 结合 **HPCC（High Precision Congestion Control，SIGCOMM 2019）** 利用交换机带内网络遥测（INT）精准感知队列深度，主动调节发送速率，**摆脱对传统无损以太网 PFC 反压的强依赖**，具备抗丢包与亚秒级故障自愈能力。
  - **实测工程收益**：根据阿里云公布的生产数据，HPN 7.0 + Solar-RDMA + ACCL 方案使大模型分布式训练端到端有效效率提升了 **14.9%**。
- **eRDMA（Elastic RDMA，弹性 RDMA）**：依托 CIPU 将 RDMA 能力普惠化到通用 ECS 实例（如倚天 `g8y`/`c8y` 及 x86 通用实例），无需采购昂贵的专有 InfiniBand 网卡即可在标准 VPC 内获得微秒级 RDMA 通信能力，非常适合分布式向量检索、Ray 集群与 CPU/GPU 混合推理。
- **ACCL（Alibaba Collective Communication Library）**：阿里云自研集合通信库（兼容 NCCL API 语义），原生感知 **“节点内 ICN/NVLink + 节点间 HPN 7.0 双平面多轨 + Solar-RDMA 多路径”** 的多层拓扑，支持通信与计算重叠（Overlap）、慢节点动态绕行与 MoE All-to-All 通信加速。

### 3.4 存储底座：CPFS（并行文件系统）与 OSS 透明数据流动

- **全对称元数据架构**：CPFS（Cloud Parallel File System）提供单文件系统最高 **1,000 万 IOPS**、**100 亿文件数**、**10 万+ 元数据 OPS** 与稳定的**亚毫秒级 I/O 时延**；吞吐能力随容量线性扩展（通用版达 20 GB/s，灵骏智算专有版可达数百 GB/s 至 TB/s 级）。
- **CPFS ↔ OSS 透明数据流动（Data Flow）**：在 AI 训练与推理中，PB 级原始语料和历史模型权重存放在低成本对象存储 OSS 中，而训练/推理容器直接通过 POSIX / NFSv3 接口挂载 CPFS。CPFS 会在后台按**数据块（Block）粒度透明懒加载（Lazy Load）** OSS 中的数据并缓存在镇岳 510 NVMe SSD 驱动的 CPFS 高速层中，业务代码无需修改一行即可兼顾 OSS 的低成本与并行文件系统的极致吞吐。

## 4. L1.5 / L2 灵骏智算平台（PAI-Lingjun）深度测评

### 4.1 平台定位与核心架构

**灵骏智算服务（PAI-Lingjun / EFLO）** 是阿里云面向大模型预训练、大规模后训练与高并发分布式推理推出的 **L1.5 级异构高密算力与智算集群底座**。它向上承接 PAI（PAI-DLC / PAI-EAS）与百炼平台，向下直接纳管 **磐久 AL128（`GP9A` 真武 PPU 超节点）**、**NVIDIA 高端 GPU 裸金属节点**、**HPN 7.0 高速网络** 与 **CPFS 智算存储**。

### 4.2 关键技术特性拆解

1. **高速网络域（HPN Zone / `hz`）亲和性保障**：
   - 在公有云上做多机训练或多机分布式推理，架构师最怕买到的机器分散在不同机房甚至不同 Pod，导致跨 Spine 跳数增加、RDMA 延迟抖动。
   - 灵骏在购买资源与创建子配额时，显式暴露了 **高速网络域（`hz`）** 概念：管理员可勾选“放置在同一高速网络域下”，或在 PAI-EAS / PAI-DLC 中开启 **HPN Zone 资源亲和性调度**，强制调度器将同一个分布式作业的所有实例收敛在同一个 HPN 7.0 超节点网络域内。
2. **双平面网卡注入（`net0` RDMA + `eth1` VPC）**：
   - 在灵骏节点上运行分布式任务时，系统自动为容器注入双网卡：**`net0`** 绑定底层 HPN 7.0 无损/Solar-RDMA 高速网络（通过环境变量 `COMM_IFNAME=net0`、`RANK_IP`、`MASTER_ADDRESS` 自动传递给 Torch Distributed / NCCL / ACCL / Ray），而 **`eth1`** 绑定用户自定义的 VPC 网络用于业务流量、数据库访问与监控上报，彻底实现计算通信面与业务控制面物理隔离。
3. **全周期硬件可观测与自动自愈（SanityCheck + 热备顶替）**：
   - 大规模 GPU/PPU 集群硬件故障率随卡数呈指数上升（掉卡、ECC 双比特显存错误、光模块劣化）。灵骏内置节点级主动巡检与被动触发自检机制：一旦发现硬件异常，自动将该节点标记为不可调度（Cordon/Drain），从用户专属池的热备水位中秒级拉起健康节点替换，并联动上层 PAI-DLC 自动从最新 Checkpoint 恢复训练。

### 4.3 灵骏智算平台优劣势评估（架构师视角）

- **核心优势**：
  - **国内极少数兼具“国际主流 GPU + 自研真武 PPU 超节点（`GP9A`）”的双轨底座**，给企业提供了应对供应链合规风险的真实备选方案；
  - **HPN 7.0 网络与 CPFS 存储原生拉通**，免去了企业自建 InfiniBand / RoCE 机房漫长的网络调优与光模块排障周期；
  - **既支持包年包月独享集群，也通过 PAI 公共资源池开放了灵骏按量付费能力**，降低了中小团队体验 RDMA 多机训推的门槛。
- **局限与短板**：
  - **地域与库存白名单限制**：灵骏资源目前集中在 **乌兰察布（主力智算大区）、北京、上海、杭州、深圳、新加坡** 6 个核心地域；旗舰机型（如 `GP9A` 超节点及高端大显存卡）普遍需要联系商务经理申请白名单或预付费锁池；
  - **偏向底层资源交付**：单独购买裸灵骏（EFLO）对团队的 Kubernetes / Slurm / NCCL 调优能力要求高，通常必须搭配上层 **PAI 平台（PAI-DLC / PAI-EAS）** 才能发挥完整的工程效率。

## 5. L2 人工智能平台 PAI（“Pi平台”）深度测评

> **术语说明**：行业交流中常被口述为 **“Pi平台”** 的产品，标准官方名称即为 **阿里云人工智能平台 PAI（Platform for AI）**。它是阿里云 L2 层的核心云原生 AI 工程平台，向下统一纳管通用计算资源（ECS/ECI/GU30）与灵骏智算资源（PAI-Lingjun），向上支撑百炼平台与企业自建训推流水线。

### 5.1 核心三大件（DSW / DLC / EAS）工程能力深度拆解

#### 5.1.1 PAI-DSW（Data Science Workshop，交互式建模工作台）
- **定位**：云端托管的 JupyterLab / VS Code Web 交互式开发环境。
- **架构亮点**：直接挂载与生产训练一致的 CPFS / NAS / OSS 存储卷与容器镜像；算法工程师在单卡/单机 DSW 中完成代码调通后，可**一键将开发环境打包并提权提交为 PAI-DLC 多机分布式训练任务**，消除了“本地能跑、上集群报错”的环境割裂。

#### 5.1.2 PAI-DLC（Deep Learning Containers，分布式训练平台）
PAI-DLC 并非简单的 K8s Job 封装，其核心竞争力在于三大内建工程组件：
1. **AIMaster（智能容错与弹性训练控制器）**：
   - 实时监控所有 Worker 的进程状态、GPU 利用率与通信心跳，精准识别 **Hang（死锁卡死）** 与 **Straggler（慢节点拖尾）**；
   - 当单节点故障时，无需销毁整个千卡 Pod 组，支持 **单节点级原地重启或单点剔除重调度**，大幅缩短故障恢复时间（MTTR）。
2. **EasyCKPT（异步多级高速 Checkpoint 框架）**：
   - 传统 PyTorch `torch.save` 在保存数百 GB 至数 TB 模型状态时会完全阻塞 GPU 训练长达数分钟。
   - `EasyCKPT` 采用 **“GPU 显存 → Host DDR5 内存秒级异步拷贝 → 后台多线程向 CPFS/OSS 刷盘”** 的两阶段流水线，将训练侧感知的 Checkpoint 停顿压缩至亚秒/秒级，使高频快照成为可能。
3. **SanityCheck（训练前/故障后硬件深度诊断）**：
   - 在正式启动昂贵的大规模分布式训练前，或检测到 NCCL/ACCL 超时后，自动在涉事节点上运行 GPU 显存 ECC、PCIe 带宽、NVLink/ICN 连通性及 RDMA 环回压测，秒级定位“坏卡/坏线”并自动重调度。

#### 5.1.3 PAI-EAS（Elastic Algorithm Service，在线模型推理平台）
PAI-EAS 是目前国内公有云在 **LLM 与 MoE 生产级推理工程化** 上打磨最深的平台之一，其四大高阶特性极具架构参考价值：

1. **多机分布式推理（`Unit` 抽象与 `unit.guard` 屏障容错）**：
   - 针对单机 8 卡装不下的万亿模型（如 DeepSeek-R1/V3 满血版、Qwen3.5-397B），EAS 引入了 **实例单元（`Unit`）** 抽象：一个 `Unit` 包含多台通过灵骏 RDMA（`net0`）互联的物理机，对外仅由 `RANK_ID=0` 承接流量，不同 `Unit` 之间完全无状态且对称扩缩容。
   - **滚动更新与容错屏障（`unit.guard: true`）**：滚动发布时以整个 `Unit` 为原子粒度并行创建新机器、就绪后整体摘流切换；当 `Unit` 内任一机器异常时，`unit.guard` 自动触发全 `Unit` 重置并通过同步屏障（Barrier）等待所有机器同时就绪后再拉起 vLLM/SGLang 进程，彻底杜绝了多机推理中常见的 NCCL 组网半死锁状态。
2. **LLM 智能路由（`LLM Gateway` + `LLM Scheduler`）**：
   - 在多实例推理集群前部置独立的 `LLM Gateway`（默认双副本高可用，**原生内置 Anthropic API → OpenAI API 协议自动转换，支持 Claude Code 直接零改造接入**）与 `LLM Scheduler`。
   - 支持四大智能调度策略：
     - **`prefix-cache`（默认推荐，基于前缀缓存亲和路由）**：优先将包含相同历史对话或固定长 System Prompt / RAG 知识库前缀的请求路由到已缓存该 KV Cache 的后端实例。根据阿里云官方在 5 实例集群上的实测数据，开启 `prefix-cache` 智能路由后，**QwQ-32B 的平均首字延迟（Mean TTFT）降低了 25.0%（从 1144.6ms 降至 859.4ms），Qwen2.5-72B 的 Mean TTFT 降低了 23.4%（从 508.6ms 降至 389.7ms），中位 TTFT 降幅更达 41.6%**；
     - **`least-token`（最少 Token 负载）**：按各实例当前正在处理的（输入+输出）Token 总数动态均衡负载；
     - **`least-request`（最少并发请求）**：适合请求长度均匀的短文本场景；
     - **`pd-split`（静态 PD 分离路由）**：将实例池拆分为独立的 Prefill 组与 Decode 组，并分别为两组配置独立子策略。
3. **MoE 专家并行（EP）+ PD 分离 + MTP 联合优化部署模板**：
   - 针对 `DeepSeek-R1/V3`、`Qwen3.5 MoE` 等稀疏模型，PAI-EAS 提供了一键式 **“EP + PD 分离 - PAI 优化版”** 模板，默认在 Prefill 组采用高张量并行（如 `TP_SIZE=8`）吃满计算单元，在 Decode 组采用大专家并行与数据并行（如 `EP_SIZE=8, DP_SIZE=8`）配合多 Token 预测（MTP）与计算-通信重叠，并支持在统一聚合视图下对 Prefill、Decode、智能路由三个子服务独立监控与弹性扩缩容。
4. **自研推理引擎 `BladeLLM` 与高性价比 `GU30` 专属机型**：
   - 除原生支持开源 `vLLM` 与 `SGLang` 外，PAI 提供自研 **`BladeLLM`** 推理引擎（针对 Qwen 系列与真武 PPU / GPU 做了深度算子融合与显存优化）；
   - 同时推出 **PAI GU 系列（首发 `GU30`，24GB 显存、31 TFLOPS FP32，性能对齐 NVIDIA A10）**，通过集群级异构池化将单卡价格较常规 A10 实例直降 **20%~45%**，并提供稠密型（`c8m30`）、平衡型（`c16m60`）、稀疏搜索推荐型（`c32m188`）及双卡/四卡规格。

### 5.2 架构师核心亮点：训推一体父子配额树（Quota Tree）与错峰潮汐抢占

![PAI 训推一体潮汐配额树与 PAI-EAS Prefix-Cache 智能路由官方实测加速比](assets/05-pai-tidal-preemption-and-eas-benchmark.svg)

企业自建或包月租赁千卡智算集群时，最大的成本黑洞是 **潮汐效应**：在线推理服务（EAS）必须按白天业务最高峰预留算力，导致夜间凌晨大量 GPU 空转；而离线预训练/微调任务（DLC）又苦于算力不足排长队。

PAI 在资源配额（Quota）层原生设计了 **“父子层级配额树 + 训推一体优先级抢占”** 机制：

```text
                [ PAI 训推一体父子配额树 (Quota Tree) 潮汐复用机制 ]

                     +-----------------------------------------+
                     |       父配额 Quota 1 (总算力池: 100卡)   |
                     |  - 绑定 PAI-EAS 在线推理服务             |
                     |  - 开启【推理服务高优抢占 (Preemption)】 |
                     +-----------------------------------------+
                                   /                     \
           白天高峰: EAS 瞬间抢占回收                      夜间低谷: 释放空闲算力供 DLC 满载训练
                                 /                         \
                                v                           v
        +-----------------------------------+   +-----------------------------------+
        |  子配额 Quota 1.1 (研发团队 A)     |   |  子配额 Quota 1.2 (研发团队 B)     |
        |  - 运行 PAI-DLC 离线微调/强化学习  |   |  - 运行 PAI-DLC 数据合成/继续预训练|
        |  - 被抢占时通过 EasyCKPT 秒级存盘 |   |  - 支持 FIFO/遍历/均衡/智能调度   |
        +-----------------------------------+   +-----------------------------------+
```

- **运行机制**：
  1. 架构师将购买的灵骏或通用计算资源创建为 **父配额 `Quota 1`**，并在此层级部署 **PAI-EAS 在线推理服务**（配置基于 QPS/队列长度的自动弹性伸缩或定时伸缩，并开启“允许抢占子配额训练作业”开关）；
  2. 在 `Quota 1` 下创建多个 **子配额（`Quota 1.1`、`Quota 1.2`）** 分配给各算法团队提交 **PAI-DLC 离线训练作业**；
  3. **夜间流量波谷**：EAS 自动缩容释放 GPU，子配额中的 DLC 作业立即吃满释放出的空闲算力；
  4. **白天流量早高峰**：EAS 触发扩容，调度器在秒级内按优先级优雅驱逐子配额中的低优 DLC 训练容器（配合 `EasyCKPT` 保存断点），将算力立即归还给在线推理，待高峰回落后 DLC 任务自动排队续训。
- **架构价值**：无需研发团队自己编写复杂的 K8s Volcano/Kueue 混部控制器，开箱即可将企业专属算力池的全天综合利用率从行业平均的 **35%~45% 拉升至 75%~85% 以上**。

### 5.3 PAI 平台优劣势评估

- **核心优势**：
  - **全生命周期闭环与高容错工程化**：从 DSW → DLC（AIMaster/EasyCKPT）→ EAS（智能路由/EP+PD 分离）再到父子配额潮汐混部，几乎覆盖了 AI Infra 团队自建平台所需的全部核心模块；
  - **拥抱开源标准与异构兼容**：全面兼容 vLLM、SGLang、Ray、Megatron-LM、DeepSpeed、OpenAI API 与 Anthropic API（Claude Code），同时屏蔽底层 NVIDIA GPU 与平头哥真武 PPU 的硬件差异。
- **局限与短板**：
  - **组件概念与配置复杂度高**：仅 EAS 的资源类型就分为“公共资源组、EAS 专属资源组、虚拟资源组、资源配额（通用计算 2.0 / 灵骏智算）”四种，且部分高阶能力（如 `LLM 智能路由`）**只能在新建服务时绑定，不支持对存量运行服务在线更新开启**，且与 NLB/Nacos 及队列服务互斥，架构师初期需要仔细规划拓扑；
  - **冷启动与大镜像拉取耗时**：在 EAS 上首次拉起大规模 MoE EP+PD 分离聚合服务（如满血版 DeepSeek-R1 优化版）部署就绪耗时约需 **30~40 分钟**，不适合秒级从零冷启动，生产环境必须保留基线常驻副本。

#### 架构师特别关注：百炼在 MaaS 层原生落地的两大高阶机制
1. **PTU 的 Prefix Cache 容量折算模型**：
   - 在传统云厂商的 PTU（如 Azure PTU / AWS Provisioned Throughput）中，长上下文多轮对话极易瞬间打爆购买的输入 TPM 额度。
   - 百炼在 PTU 中直接将 **Prefix Cache 命中率与 KTPM 容量扣减挂钩**：例如 `qwen3.8-max` 的缓存折扣系数为 **`0.125`（即命中 Prefix Cache 的历史 Token 仅消耗 12.5% 的 PTU 输入额度）**，`deepseek-v4-pro` 低至 **`0.08`（仅消耗 8% 额度）**，`qwen3.7-plus` 为 **`0.2`（20%）**。以 50K 输入、前 30K 命中缓存为例，可直接节省 **43%** 的 PTU 购买容量，配合 `x-dashscope-ptu-overflow:true` 自动溢出到按量计费，是金融客服、代码助手等固定长前缀高并发场景的极佳 FinOps 设计。
2. **MU（模型单元）直接暴露 `PD 分离计算模式`**：
   - 针对 `qwen3.5-397b-a17b`（`MU1 x 16` 或 `MU3 x 16 PD分离模式`）、`qwen3.6-plus`（`MU3 x 16 PD分离模式`）、`deepseek-v3.2`（`MU2 x 16 PD分离模式`）、`glm-5`（`MU3 x 16 PD分离模式`）等超大规模模型，百炼在 MU 专属部署中直接提供了一键勾选的 **PD 分离模式**，在底层自动将计算密集型的 Prefill 节点与访存密集型的 Decode 节点物理拆开部署，使不懂底层分布式引擎的企业也能直接获得首字延迟（TTFT）与解码吞吐（TPOT）解耦的生产级性能。

## 7. AI Infra 架构师综合评估：核心优势、短板风险、云厂商横向对比与选型决策树

### 7.1 阿里云 AI Infra 的五大核心架构壁垒（Strengths）

1. **“通-云-哥”全栈协同带来的正向飞轮（Co-Design Flywheel）**：
   - 阿里同时拥有顶尖开源/闭源大模型研发团队（通义千问 Qwen）、超大规模云基础设施（阿里云 HPN 7.0 / CIPU / PAI）与自研芯片团队（平头哥真武 PPU / 倚天 CPU / ICN Switch / 磐脉网卡 / 镇岳主控）。
   - **架构体现**：Qwen3.5/3.8 的 MoE 专家切分粒度与激活比直接指导了真武 M890/V900 的 **144GB/216GB 大显存 + 800/1200 GB/s ICN 带宽** 设计；而镇岳 510 的 ZNS+QLC 与 PAI-EAS 的 Prefix-Cache 智能路由又反哺了百炼平台上百万 Token 长上下文的低成本落地。
2. **直面大模型真实瓶颈的“高显存 + 超节点 Scale-Up”路线**：
   - 在单芯片受制于先进光刻机代差的大背景下，平头哥没有陷入单纯堆砌单卡稠密 FP16 TFLOPS 的死胡同，而是通过 **真武 M890（144GB HBM3）→ V900（216GB HBM）+ ICN Switch 1.0（25.6T，<150ns 延迟，Load/Store 统一编址）+ 磐久 AL128（64/128 卡超节点）**，优先攻克了万亿 MoE 模型与长文本推理中最卡脖子的 **显存容量墙（Memory Capacity Wall）** 与 **片间通信墙（Interconnect Wall）**。
3. **经过顶会验证与十万卡级生产锤炼的 HPN 7.0 以太网智算架构**：
   - 相比昂贵且封闭的 InfiniBand，阿里云 **HPN 7.0（双上联 + 多轨 + 双平面）+ Solar-RDMA（多路径包喷洒 + HPCC）+ ACCL** 证明了基于标准高密以太网交换芯片（51.2 Tbps）同样可以在两层 Clos 下实现 15,000+ 卡无收敛互联，并在容忍光模块/ToR 故障的同时取得 **+14.9%** 的训练效率增益。
4. **PAI 平台在“潮汐混部”与“MoE/PD 分离推理”上的成熟工程化封装**：
   - **父子配额树（Quota Tree）训推一体抢占** + **EasyCKPT 秒级异步断点** + **EAS LLM 智能路由（降低 23%~25% TTFT）** + **EP+PD 分离一键模板**，将原本只有头部大厂 Infra 团队才能玩转的高阶优化变成了云控制台上的标准配置项。
5. **百炼平台在算力金融化（Token / PTU / DTU / MU）上的精细颗粒度**：
   - 尤其是 **PTU 的 Prefix Cache 容量折算折扣 + 自动溢出机制**，以及 **MU/DTU 对全参微调模型和 PD 分离的原生支持**，让企业从 PoC 走向生产高并发时拥有极其平滑的成本演进曲线。

### 7.2 架构师必须警惕的五大工程短板与风险边界（Weaknesses & Risks）

1. **平头哥 SAIL 软件栈 vs NVIDIA CUDA 的长尾生态代差**：
   - 尽管真武 PPU（810E/M890）累计出货已超 56 万片并完美跑通了 Qwen、DeepSeek、Kimi 等主流 Transformer/MoE 架构，但对于依赖大量 **手写 CUDA C++ / PTX 内核、Triton 自定义非标算子、3D 高斯泼溅（3DGS）、复杂物理仿真或前沿非 Transformer 架构** 的科研与垂直业务，平头哥 SAIL 软件栈的算子覆盖率、调试工具链（Profiling/Debugging）与社区生态与 CUDA 仍有明显差距，直接迁移需预留专门的算子适配人月。
2. **真武 PPU 单芯片峰值算力未公开与重度计算密集型（Compute-Bound）场景权衡**：
   - 平头哥官方至今未公开真武 810E/M890/V900 的精确单卡 FP16/BF16/FP8 TFLOPS 数值（仅提供代际 3× 倍率）。在**超长输入但极短输出、且无法命中 Prefix Cache 的重度 Prefill 计算密集型场景**，或者高密度稠密矩阵乘法（GEMM）场景下，单卡裸算力密度是否能与国际最新旗舰（如 NVIDIA B200）持平，必须通过企业自有真实 Workload 压测（如使用 `EvalScope`）实测检验，切忌仅凭显存容量拍板。
3. **旗舰智算资源地域集中与白名单/配额锁定约束**：
   - 灵骏智算资源目前仅开放 6 个地域（乌兰察布、北京、上海、杭州、深圳、新加坡），且 `GP9A` 超节点、高配 DTU 及部分新模型（如 `qwen3.7-flash` PTU）需要联系商务经理申请白名单或签订包月预付费合同，不具备传统公有云 CPU 实例“全球任意可用区随开随用”的完全自助弹性。
4. **运维接口割裂与退订商务惩罚成本**：
   - 百炼 **DTU 独占吞吐目前仅支持在控制台手工创建与扩缩容，不支持通过 API/Terraform 自动化编排**；
   - PAI-EAS 的 **LLM 智能路由只能在新建服务时配置，无法对存量线上服务热升级挂载**；
   - 百炼 PTU / DTU / MU 的预付费订单若提前退订，**已使用时长部分需按 `1.2 倍` 惩罚系数结算退费**，容量规划失误会带来直接财务损耗。
5. **深度全栈专有协议带来的云厂商锁定（Vendor Lock-in）**：
   - 阿里云的高性能优势高度依赖 **`ICN 片间互联 + CIPU + Solar-RDMA + ACCL + CPFS + BladeLLM`** 这一套垂直耦合栈。一旦业务深度绑定这套专有接口或百炼 DTU/MU 模板，后续若需向 AWS、本地 IDC 自建 Kubernetes 或其他国产算力平台做多云双活迁移，底层基础设施层与推理部署层需要较大规模重构。
